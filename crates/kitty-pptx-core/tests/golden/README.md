# Golden-image E2E tests

Reference pixels and protocol streams that guard the entire deck-to-terminal
pipeline. The tests are intentionally boring: no mocks, no hand-written vector
scenes. Every PNG golden goes through the production seam used by the CLI:

```
.pptx -> DefaultPresentationLoader -> DefaultSlideCompiler::compile_in_deck
      -> TinySkiaRasterizer::rasterize -> RGBA8 -> PNG
```

## Layout

```
tests/
  golden_tests.rs              # core PNG golden harness + region invariants
  golden_support/mod.rs        # shared deck table, render cache, compare metrics
  golden/
    README.md                  # this file
    fixtures/                  # committed .pptx inputs (8 decks, 19 slides)
    png/<deck>/slide_NNN.png   # committed reference renders (19 files)
    gen_fixture.py             # deterministic synthetic e2e deck generator
    gen_pptxgenjs.js           # pptxgenjs fixture generator (needs npm)
    probe_png.py               # dev-only PNG/region colour probe
    decode_halfblock.py        # dev-only half-block ANSI decoder
```

The terminal-stream tests live in
`crates/kitty-pptx-display/tests/golden_stream_tests.rs` and use a synthetic
8x6 `RgbaSlide` so they stay font- and fixture-independent.

## Fixed render spec

Each deck is rendered at a fixed `width_px = 800`; the height is derived from
the deck's slide aspect ratio and rounded deterministically:

| Deck | Slides | Golden size |
| --- | ---: | --- |
| `e2e_deck` | 5 | 800x450 |
| `pptxgenjs_sample` | 6 | 800x450 |
| `sample` | 2 | 800x450 |
| `KEY02` | 1 | 800x450 |
| `ShapePlusImage` | 1 | 800x533 |
| `chart_pt_color_bg1` | 1 | 800x450 |
| `smartart-org-chart` | 1 | 800x600 |
| `ArtisticEffectSample` | 2 | 800x450 |

The spec table (width and thresholds) is `DECKS` in `golden_tests.rs`.

## Regenerating goldens

After an intentional renderer change, or after changing the font stack:

```sh
UPDATE_GOLDENS=1 cargo test -p kitty-pptx-core --test golden_tests
```

The test writes every image under `tests/golden/png/<deck>/slide_NNN.png`,
prints each path, and still passes. Review the resulting image diff and commit
the new PNGs. Running without `UPDATE_GOLDENS` compares pixels.

Missing golden files are a hard failure with a pointer back to this command;
they are committed assets, not build output.

## Comparison thresholds

`golden_support::diff_metrics` computes, over all RGBA bytes:

- `mean_abs_diff`: mean absolute per-channel difference (0..=255 scale).
- `outlier_fraction`: fraction of pixels whose largest channel delta exceeds
  `channel_tolerance`.

Default policy: `mean_abs_diff <= 2.0`, `outlier_fraction <= 0.02` with
`channel_tolerance = 12`. `ArtisticEffectSample` uses the looser
`4.0 / 0.05 / 16` policy because it exercises resvg image filters and artistic
effects. Thresholds are per-deck and live in the `DECKS` table.

The policy is deliberately strict enough that a real renderer regression
(wrong fill, missing shape, shifted layout, broken image decode) fails, while
sub-pixel anti-aliasing jitter does not. A different font stack is *not*
anti-aliasing jitter: regenerate goldens and review the diff.

## Font dependency

Goldens were generated on Linux with **DejaVu Sans 2.37**
(`fonts-dejavu-core`) as the only installed family. The compiler substitutes
Calibri/Arial/Segoe UI with the best available system face, so:

- Goldens must be regenerated when the installed font family/version changes.
- CI images that render text-heavy decks (`pptxgenjs_sample`, `KEY02`,
  `ArtisticEffectSample`, chart labels) need DejaVu Sans installed to match.
- Font-independent coverage lives in
  `e2e_slide1_solid_regions_match_ground_truth` and
  `e2e_slide2_background_gradient_is_light_towards_bottom_right`. These assert
  solid shape fills and gradient direction without any golden files.

## Fixtures

- `e2e_deck.pptx` is generated by `gen_fixture.py` using only the Python
  standard library. The zip is byte-stable (fixed timestamps and part order):

  ```sh
  python3 crates/kitty-pptx-core/tests/golden/gen_fixture.py
  ```

- `pptxgenjs_sample.pptx` is generated by `gen_pptxgenjs.js`:

  ```sh
  cd crates/kitty-pptx-core/tests/golden
  npm i pptxgenjs
  NODE_PATH="$PWD/node_modules" node gen_pptxgenjs.js
  ```

- `sample.pptx`, `KEY02.pptx`, `ShapePlusImage.pptx`,
  `chart_pt_color_bg1.pptx`, `smartart-org-chart.pptx` and
  `ArtisticEffectSample.pptx` are static real-world inputs; no generator.

Generators are development tools and are not invoked by `cargo test`. If a
generator bug changes fixture bytes, commit the regenerated deck together
with the refreshed goldens.

## Terminal-stream goldens

`kitty-pptx-display/tests/golden_stream_tests.rs` captures real driver output
by re-invoking the test binary in a child process (drivers write to stdout).
Parsers decode the captured bytes back into cells/chunks and assert:

- Half-block: every `▀` cell's foreground/background maps back to the source
  top/bottom pixel (including alpha blending) at the correct cursor cell.
- Kitty stage: APC chunks parse, control keys are present, and the payload
  decodes to the source image. The test accepts the current PNG payload
  (`f=100`) and the planned raw-RGBA payload (`f=32`).
- Kitty present: cursor positioning plus `a=p,i=,c=,r=`.
- Kitty placeholders: image id in the foreground, cell offsets in the
  background, OSC 8 links only on covered cells.
- Sixel: cursor positioning plus a well-formed DCS stream. Raster attributes
  (`"1;1;W;H`) are required by the PRD but the current display encoder does
  not emit them; `sixel_stream_includes_raster_attributes` is ignored until
  the display crate implements them.

## Dev-time probes

`probe_png.py` decodes a PNG and prints average colours for fractional sample
points; `decode_halfblock.py` turns captured half-block ANSI into a colour
grid. They are diagnostics, not test dependencies.
