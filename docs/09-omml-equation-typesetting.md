# PRD 09: Live OMML Equation Typesetting Engine

> Extends the typography and vector composition architecture ([PRD 02a](./02a-composition-core-and-render-pipeline.md), [PRD 02c](./02c-typography-and-text-layout.md), [PRD 02d](./02d-element-renderers-and-fidelity-policy.md)). Specifies native mathematical typesetting for Office Math Markup Language (OMML / ECMA-376 §22.1) `<m:oMath>` and `<m:oMathPara>` trees into resolution-independent `VectorSlide` display list commands. Normative interfaces live in [PRD 06](./06-component-interface-contracts.md).

---

## 1. Executive Summary & Architectural Seam

### 1.1 From Static Raster Fallbacks to Live Typesetting
Previously, OMML equations in **Office Terminal** relied on authoring-time raster previews (`math_fallback` images embedded by PowerPoint inside `mc:AlternateContent` blocks). While this provided baseline compatibility, raster previews exhibit severe deficiencies:
1. **Resolution Degradation**: Fixed 96/150 DPI raster previews blur and pixelate on 4K/retina terminal displays and high-DPI export canvases.
2. **Missing Vector Export**: SVG export was forced to embed bulky, non-selectable raster bitmaps instead of clean vector text and paths.
3. **Missing Fallbacks in Third-Party Decks**: Presentations generated by LibreOffice, Google Slides, Python-pptx, or pandoc frequently omit `mc:Fallback` images entirely, leaving equations as empty placeholders.

This specification establishes **Live OMML Equation Typesetting** directly within `office-terminal-core`. The engine parses raw OMML XML or the validated `pptx-model` math AST, executes a TeX-style box-and-glue layout algorithm parameterized by OpenType `MATH` table font metrics, and emits native `DrawText` (`PositionedGlyphRun`) and `DrawPath` (`VectorPath`) commands onto the `VectorSlide` display list.

### 1.2 Inline vs. Display Math Seams
OMML equations appear in two structural contexts within PresentationML text bodies:
- **Display Math (`<m:oMathPara>`)**: Standalone, paragraph-level mathematical blocks (`display: true`). They participate in vertical paragraph layout, respecting slide alignment (centered by default, or left/right aligned via `m:jc`), with dedicated vertical spacing above and below.
- **Inline Math (`<m:oMath>`)**: Mathematical fragments embedded directly within running paragraph text (`display: false`). They are measured as atomic inline boxes (`InlineMathBox`) embedded within `cosmic-text` text shaping buffers, aligned precisely along the paragraph baseline ($y = 0$).

## 2. OMML AST & Element Taxonomy

The typesetting engine processes the unified `MathNode` AST defined in `ooxml-common` / `pptx-model`. Each node maps to distinct TeX layout semantics:

### 2.1 Element Mapping & Layout Rules

| OMML Element | AST Variant | TeX Equivalent | Layout & Dimensional Semantics |
| :--- | :--- | :--- | :--- |
| `<m:f>` | `Fraction` | `\frac{num}{den}` | Fraction bar thickness $\sigma$, numerator rise, denominator drop. |
| `<m:rad>` | `Radical` | `\sqrt[deg]{rad}` | Radical symbol $\surd$ with vertical extension and top horizontal vinculum. |
| `<m:sSub>` | `Sub` | `x_{sub}` | Downward baseline shift $\Delta y_{sub}$, optical scale ($0.70\times$). |
| `<m:sSup>` | `Sup` | `x^{sup}` | Upward baseline shift $\Delta y_{sup}$, optical scale ($0.70\times$). |
| `<m:sSubSup>` | `SubSup` | `x_{sub}^{sup}` | Unified script column with anti-collision vertical clearance. |
| `<m:sPre>` | `SPre` | `{}_{sub}^{sup}x` | Leading subscript/superscript positioned before the base box. |
| `<m:nary>` | `Nary` | `\sum`, `\int`, `\prod` | Big operator glyph; limits positioned either above/below or as sub/sup. |
| `<m:d>` | `Delimiter` | `\left( ... \right)` | Delimiters stretch vertically to cover enclosed box height. |
| `<m:m>` | `Array` (Matrix) | `\begin{matrix}` | 2D table grid with uniform column alignment and row spacing. |
| `<m:eqArr>` | `Array` (EqArray) | `\begin{align}` | Multi-line equation array aligned at relation signs ($=$). |
| `<m:acc>` | `Accent` | `\hat{x}`, `\vec{x}` | Accent mark centered above base, compensated for font italic slant. |
| `<m:func>` | `Func` | `\sin`, `\lim`, `\log` | Upright operator function name followed by thin space and argument. |
| `<m:borderBox>`| `BorderBox` | `\boxed{x}` | Rectangular or partial enclosure border around expression. |
| `<m:phant>` | `Phant` | `\vphantom`, `\hphantom` | Transparent spacing box controlling layout dimensions. |

### 2.2 Fractions (`<m:f>`)
Fractions consist of a numerator (`<m:num>`), denominator (`<m:den>`), and optional properties (`<m:fPr>`):
- **Bar Types**:
  - `bar` (Standard): Horizontal rule of thickness $t_{rule}$ centered at the math axis height $a_{math}$.
  - `noBar` (Stacked / Binomial): Fraction bar suppressed ($t_{rule} = 0$), e.g. $\binom{n}{k}$.
  - `skw` (Skewed): Numerator and denominator separated by a diagonal slash glyph ($/$).
  - `lin` (Linear): Horizontal in-line layout ($num / den$).
- **Rule Geometry**:
  $$\text{Width} = \max(w_{num}, w_{den}) + 2 \cdot \delta_{margin}$$
  $$\text{Numerator Baseline Shift}: \quad y_{num} = a_{math} + \sigma_{num\_shift}$$
  $$\text{Denominator Baseline Shift}: \quad y_{den} = a_{math} - \sigma_{den\_shift}$$
  Where $\delta_{margin} = 0.12 \cdot \text{font\_size}$ provides optical horizontal overrun.

### 2.3 Radicals (`<m:rad>`)
Radicals contain an optional degree index (`<m:deg>`) and a radicand (`<m:e>`):
1. **Radical Symbol ($\surd$)**: Selected from the OpenType `MATH` table glyph construction table (`radicalVariants` or assembled vertically via `radicalAssembly`).
2. **Vinculum (Overbar)**: A horizontal rule of thickness $t_{rule} = \text{RadicalRuleThickness}$ drawn from the top tip of the radical symbol across the full width of the radicand:
   $$x_{start} = x_{symbol} + w_{symbol}, \quad x_{end} = x_{start} + w_{radicand} + \delta_{pad}$$
3. **Degree Positioning**: When `<m:deg>` is present, it is rendered in ScriptScript style ($0.50\times$ font size) nested inside the radical's left notch:
   $$x_{deg} = x_{symbol} + \text{RadicalDegreeBottomRaisePercent} \cdot w_{symbol}$$
   $$y_{deg} = y_{vinculum} - \text{RadicalKernBeforeDegree}$$

### 2.4 Scripts & Pre-scripts (`<m:sSub>`, `<m:sSup>`, `<m:sSubSup>`, `<m:sPre>`)
- **Optical Font Scaling**: Subscripts and superscripts are scaled by $S_{script} = 0.70$ (level 1) or $S_{script2} = 0.50$ (level 2).
- **Clearance Anti-Collision**: When both sub and sup exist on a base (`<m:sSubSup>`), the vertical gap between the bottom of the superscript box and the top of the subscript box must satisfy:
  $$\text{gap} = (y_{sup} - d_{sup}) - (y_{sub} + h_{sub}) \ge \text{SubSupGapMin}$$
  If $\text{gap} < \text{SubSupGapMin}$, $y_{sup}$ is shifted upwards and $y_{sub}$ is shifted downwards by half the deficiency.
- **Pre-scripts (`<m:sPre>`)**: Positioned immediately before the base box, aligning right edges to the base box's left boundary.

### 2.5 N-ary Operators (`<m:nary>`)
Covers $\sum$, $\prod$, $\int$, $\iint$, $\oint$, $\bigcup$, $\bigcap$:
- **Operator Glyph Selection**: Display math selects the large display variant (`DisplayOperatorMinHeight`), whereas inline math uses the standard text-size glyph.
- **Limit Positioning (`limLoc`)**:
  - `undOvr` (Under/Over): Limits placed centrally above and below the operator glyph (standard for $\sum$ in display math).
  - `subSup`: Limits placed as traditional subscripts and superscripts to the right of the operator (standard for integrals $\int_a^b$ and inline math).

### 2.6 Extensible Delimiters (`<m:d>`)
Encloses content within delimiters (e.g. `(`, `)`, `[`, `]`, `{`, `}`, `|`, `‖`, `⟨`, `⟩`):
- **Dynamic Sizing**: The inner height $H_{inner} = h_{content} + d_{content}$ is computed.
- **Glyph Assembly**: If the required height exceeds standard font glyphs, the delimiter is assembled from OpenType vertical components (top, middle, bottom, and repeatable extender pieces) or synthesized via parametric Bézier paths when font assemblies are absent.
- **Centering**: The stretched delimiters are vertically centered around the formula math axis $a_{math}$.

### 2.7 Matrices & Alignment Arrays (`<m:m>`, `<m:eqArr>`)
- **Matrix (`<m:m>`)**: Formatted as an $R \times C$ rectangular grid of cells. Column widths $W_c = \max_{r} w_{r, c}$ are computed, with configurable column gap ($G_{col}$) and row gap ($G_{row}$).
- **Equation Array (`<m:eqArr>`)**: Multi-line equation block where each equation line is split around relation symbols ($=, \le, \ge, \approx, \to$). The left expressions are right-aligned and right expressions are left-aligned along a shared vertical anchor.

### 2.8 Accents (`<m:acc>`)
- Accents (e.g. $\hat{x}$, $\bar{x}$, $\tilde{x}$, $\dot{x}$, $\ddot{x}$, $\vec{x}$, $\overbrace{x}$) are positioned horizontally centered over the base:
  $$x_{acc} = x_{base} + \frac{w_{base} - w_{acc}}{2} + \kappa_{skew}$$
  where $\kappa_{skew}$ is the base glyph's OpenType italic math skew.
- The accent rests above the base box with a vertical gap $\ge \text{AccentBaseHeight}$.

## 3. TeX-Style Math Layout Engine & Font Metrics

### 3.1 The Box-and-Glue Layout Model
The layout engine compiles the OMML AST into a hierarchical tree of rectangular metric boxes:

```rust
#[derive(Clone, Debug)]
pub enum MathBox {
    /// Horizontal composition of boxes placed sequentially along the baseline
    HBox {
        width: f32,
        height: f32, // Distance above baseline (EMU)
        depth: f32,  // Distance below baseline (EMU)
        children: Vec<(f32, MathBox)>, // (x_offset, box)
    },
    /// Vertical composition of boxes (e.g. fraction, undOvr limits)
    VBox {
        width: f32,
        height: f32,
        depth: f32,
        children: Vec<(f32, MathBox)>, // (y_offset, box)
    },
    /// Single shaped mathematical glyph
    Glyph {
        font_id: fontdb::ID,
        font_family: String,
        glyph_id: u16,
        font_size_pt: f32,
        width: f32,
        height: f32,
        depth: f32,
        italic_correction: f32,
        color: [u8; 4],
    },
    /// Solid vector rule (fraction bars, square root vinculum, enclosures)
    Rule {
        width: f32,
        height: f32, // Thickness (EMU)
        color: [u8; 4],
    },
    /// Flexible or fixed horizontal/vertical spacing
    Space {
        width: f32,
        height: f32,
        depth: f32,
    },
}
```

### 3.2 Math Styles & Script Levels
Following Donald Knuth's TeX Appendix G specification, layout rules vary across eight distinct math styles:

$$\begin{array}{llll}
\mathcal{D} \text{ (Display)} & \mathcal{T} \text{ (Text)} & \mathcal{S} \text{ (Script)} & \mathcal{SS} \text{ (ScriptScript)} \\
\mathcal{D}' \text{ (Cramped D)} & \mathcal{T}' \text{ (Cramped T)} & \mathcal{S}' \text{ (Cramped S)} & \mathcal{SS}' \text{ (Cramped SS)}
\end{array}$$

- **Style Inheritance**:
  - In a fraction $\frac{N}{D}$: if parent is $\mathcal{D}$, $N$ is styled in $\mathcal{T}$ and $D$ in $\mathcal{T}'$. If parent is $\mathcal{T}$, $N$ is styled in $\mathcal{S}$ and $D$ in $\mathcal{S}'$.
  - In a radical $\sqrt{E}$: $E$ is styled in the cramped variant of the parent style (e.g. $\mathcal{D} \to \mathcal{D}'$).
  - In superscripts $X^S$: $S$ is styled in the script style corresponding to the parent (e.g. $\mathcal{D} \to \mathcal{S}$, $\mathcal{S} \to \mathcal{SS}$).

### 3.3 OpenType MATH Table Font Metrics
The layout engine queries the OpenType `MATH` table (`math` table tag) via `read-fonts` / `skrifa`. The font hierarchy prioritizes:
1. **Bundled Fallback Math Font**: **`STIX Two Math`** (SIL OFL, bundled in-binary via `include_bytes!`), ensuring guaranteed pixel-identical mathematical layout on all platforms without external dependencies.
2. **System Math Fonts**: `Cambria Math` (Windows standard), `Latin Modern Math`, `TeX Gyre Pagella Math`.

#### Key OpenType MATH Constants Extracted
```rust
#[derive(Clone, Copy, Debug)]
pub struct MathConstants {
    pub axis_height: f32,
    pub fraction_numerator_shift_up: f32,
    pub fraction_numerator_display_style_shift_up: f32,
    pub fraction_denominator_shift_down: f32,
    pub fraction_denominator_display_style_shift_down: f32,
    pub fraction_num_gap_min: f32,
    pub fraction_denom_gap_min: f32,
    pub fraction_rule_thickness: f32,
    pub radical_vertical_gap: f32,
    pub radical_display_style_vertical_gap: f32,
    pub radical_rule_thickness: f32,
    pub radical_extra_ascender: f32,
    pub subscript_shift_down: f32,
    pub superscript_shift_up: f32,
    pub superscript_shift_up_cramped: f32,
    pub sub_superscript_gap_min: f32,
    pub lower_limit_gap_min: f32,
    pub upper_limit_gap_min: f32,
    pub delimited_sub_formula_min_height: f32,
}
```

When rendering with a non-MATH font, synthesized fallback constants are derived proportionally from font em-size ($1\text{ em} = \text{font\_size\_pt} \times 12,700\text{ EMU}$):
- $\text{axis\_height} = 0.25 \cdot \text{em}$
- $\text{fraction\_rule\_thickness} = 0.05 \cdot \text{em}$
- $\text{fraction\_num\_gap\_min} = 0.15 \cdot \text{em}$
- $\text{radical\_vertical\_gap} = 0.16 \cdot \text{em}$

### 3.4 Knuth Appendix G Exact Layout Algorithms

#### Algorithm 1: Fraction Typesetting (TeX Rule 11)
```rust
pub fn layout_fraction(
    num: &MathBox,
    den: &MathBox,
    style: MathStyle,
    constants: &MathConstants,
    color: [u8; 4],
) -> MathBox {
    let thickness = if style.has_bar() { constants.fraction_rule_thickness } else { 0.0 };
    let (shift_up, shift_down) = if style.is_display() {
        (constants.fraction_numerator_display_style_shift_up, constants.fraction_denominator_display_style_shift_down)
    } else {
        (constants.fraction_numerator_shift_up, constants.fraction_denominator_shift_down)
    };

    let actual_num_shift = shift_up.max(constants.axis_height + thickness / 2.0 + constants.fraction_num_gap_min + num.depth());
    let actual_den_shift = shift_down.max(thickness / 2.0 + constants.fraction_denom_gap_min + den.height() - constants.axis_height);

    let content_w = num.width().max(den.width());
    let margin = 0.12 * constants.axis_height;
    let total_w = content_w + 2.0 * margin;

    let num_x = (total_w - num.width()) / 2.0;
    let den_x = (total_w - den.width()) / 2.0;

    let mut children = vec![
        (0.0, actual_num_shift, num.clone()),
        (0.0, -actual_den_shift, den.clone()),
    ];
    if thickness > 0.0 {
        let rule = MathBox::Rule { width: total_w, height: thickness, color };
        children.push((0.0, constants.axis_height - thickness / 2.0, rule));
    }
    MathBox::HBox { width: total_w, height: actual_num_shift + num.height(), depth: actual_den_shift + den.depth(), children }
}
```

## 4. Dual-Backend Execution

Once the `MathBox` tree is laid out, the compiler traverses the hierarchy starting at equation origin $(X_{origin}, Y_{origin})$ and flattens it directly into `VectorCommand`s:

```
                  ┌───────────────────────────────┐
                  │ Flattened MathBox Hierarchy   │
                  └───────────────┬───────────────┘
                                  │
         ┌────────────────────────┴────────────────────────┐
         │                                                 │
         ▼ (Glyph Boxes)                                   ▼ (Rule Boxes)
┌─────────────────────────────────┐               ┌─────────────────────────────────┐
│ VectorCommand::DrawText         │               │ VectorCommand::DrawPath         │
│ - PositionedGlyphRun            │               │ - VectorPath (Rectangle/Poly)   │
│ - Font ID + Size + straight RGBA│               │ - Solid Fill Paint (Straight)   │
│ - Precise EMU (x, y) baseline   │               │ - Exact EMU dimensions          │
└─────────────────────────────────┘               └─────────────────────────────────┘
```

### 4.1 Terminal & PNG Rasterization (`tiny-skia` + `swash`)
- **Glyphs**: Emitted as `VectorCommand::DrawText`. The `tiny-skia` rasterizer leverages `swash` to blit alpha-masked glyphs at subpixel precision directly to the canvas buffer.
- **Rules & Geometry**: Fraction bars and radical vinculums are emitted as `VectorCommand::DrawPath` rectangles. Because coordinates are expressed in EMUs, `tiny-skia` renders razor-sharp 1-pixel rules without subpixel fuzz or rounding artifacts.

### 4.2 Standalone SVG Export Serializer
For standalone vector SVG export, the serializer outputs clean, grouped SVG markup:

```xml
<g class="math-equation" data-math-display="true" transform="translate(1440000, 2160000)">
  <!-- Fraction bar rule -->
  <line x1="0" y1="12700" x2="182400" y2="12700" stroke="#000000" stroke-width="1270" stroke-linecap="square" />
  
  <!-- Numerator text run -->
  <text x="45200" y="-8400" font-family="STIX Two Math" font-size="18pt" fill="#000000">-b ± √(b² - 4ac)</text>
  
  <!-- Denominator text run -->
  <text x="68100" y="32500" font-family="STIX Two Math" font-size="18pt" fill="#000000">2a</text>
</g>
```
When configured with `--svg-text-mode glyph-paths`, all mathematical glyphs are converted to vector `<path d="...">` outlines, ensuring 100% visual fidelity even when viewers do not have math fonts installed.

## 5. Error Handling & Robustness

### 5.1 Graceful Fallback Hierarchy
Mathematical typesetting must never cause a presenter crash or render failure. The engine enforces a 3-tier fallback strategy:

```
[OMML Node Tree] ──► Parse & Layout ──► SUCCESS ──► Emit Live Vector Slide Commands
                           │
                         FAIL (Corrupt XML / Missing Glyphs / Depth Exceeded)
                           ▼
             [Check authoring-time `math_fallback`?]
              ├── YES ──► Emit VectorCommand::DrawImage (Legacy Raster Preview)
              │           Log WarningEvent::MathFallbackUsed
              └── NO  ──► Emit Vector Degraded Math Placeholder (PRD 02d)
                          Log WarningEvent::MathTypesettingFailed
```

### 5.2 Resource Guards & Security Limits
Adversarially crafted presentations with cyclic or hyper-deeply nested equations are neutralized via strict compile-time guards:
- **Recursion Depth Limit**: Maximum AST nesting depth is capped at **$\le 64$**. Any expression exceeding 64 levels triggers immediate fallback.
- **Node Count Budget**: Maximum node count per equation block is capped at **2,048 nodes**.
- **Dimension Clamping**: All box dimensions are validated against `f32::is_finite()`. Negative widths or NaN coordinates are clamped to zero.
